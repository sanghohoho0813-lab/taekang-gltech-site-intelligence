**배포 전 자동 점검**: `npx vercel env pull .env.preflight` → `node --env-file=.env.preflight scripts/preflight.mjs`.
- 운영 모드, 연결 문자열(풀러·SSL), 공개 변수 비밀값, 설정 코드, DB 스키마·**RLS**를 확인합니다. ❌가 없어야 배포합니다.
- `.env.preflight`는 비밀값이 들어 있으므로 확인 후 지웁니다. 저장소에는 올라가지 않게 설정돼 있습니다.

**코드를 바꾼 뒤 배포 전**: 로컬·테스트용 Postgres 주소로 `TEST_DATABASE_URL=postgres://… npx vitest run`을 돌립니다(테스트가 임시 DB를 스스로 만들고 지움 · 운영 DB 주소는 넣지 마세요). 내장 DB(PGlite)에서는 통과해도 실제 Postgres에서만 생기는 오류가 두 번 있었습니다(D-41 데이터 이중 저장, D-42 동시 첫 시작 충돌).

**배포 직후**: `npm run smoke -- https://배포주소`를 돌립니다(D-44). 로그인하지 않고 공개 주소만 확인하며 회사 데이터를 읽거나 바꾸지 않습니다.
- 확인하는 것: 운영 모드·DB 연결·스키마, 보안 헤더(CSP·HSTS 등), 로그인 없이 데이터·백업·쓰기 차단, 다른 사이트 요청 차단, 최초 설정 코드, 알림 키, 홈 화면 앱 파일, 보고서 링크(없는 주소는 열리지 않고 받는 분 화면은 로그인 없이 열림 · D-73), 하자 접수 링크(없는 주소는 열리지도 접수되지도 않음 · D-74)
- 보고서 링크(D-73)는 환경변수가 따로 필요 없습니다. DB에는 색인 하나가 자동으로 추가됩니다(스키마 2번 — 앱이 DB에 연결할 때 스스로 적용).

- 돈 기록 바로잡기(D-89)도 환경변수·스키마 변경이 없습니다(새 묶음 `receivableAdjustments`·`voidedMoney`는 기존 `records` 표). 장부 이관 때 **이미 받은 유보금·공제가 있는 현장**은 기성·입금을 넣은 뒤 ‘유보금·공제 등록’으로 따로 넣고(뗀 기성 회차·받을 날), 회사 세무사에게 지체상금 부가세 처리(시스템은 부가세 없는 돈으로 계산)와 선급금 처리 방식을 한 번 확인받으세요. 첫 달 마감 때 엑셀 ‘남은 유보금’·‘취소한 기록’ 시트를 회계 담당과 같이 보세요.
- 변경공사 증빙 파일(D-88)도 환경변수·스키마 변경이 없습니다(새 묶음 `coEvidence`는 기존 `records` 표, 원본은 사진과 같은 `photo_blobs` 표). **PDF(최대 3MB)·서류 사진(약 0.3~1MB)이 DB 용량을 씁니다** — Supabase 무료 플랜 DB 한도(500MB)에 가까워지면 유료 플랜이나 파일 저장소 이전을 검토하세요(대표 승인 · 비용). 첫 주에 공무에게 ‘승인 반영 → 날인본 첨부’를 한 번 같이 해 보고, 시스템 전 승인 건은 ‘종이로 보관 중’(보관 위치)으로 정리하게 안내하세요. 승인된 변경공사의 변경계약서·공문은 대표만 지우거나 종류를 바꿀 수 있습니다. 사진 백업 ZIP에 함께 들어가므로 계정 이전(4-1절) 때 따로 할 일은 없습니다.
- 대표 보고서 달별 보기(D-83)도 환경변수·스키마 변경이 없습니다(기성·입금에 `createdAt`·`createdBy`, 원가에 `frozenOver`, 마감 기록 현장 숫자에 `profitNet`이 붙지만 JSON 안). 대표에게 매달 초 ‘대표 보고서 → 보기 → 지난달’ 또는 월 마감의 ‘대표 보고서’ 바로 가기로 그 달 한 장을 보고, 맨 위 ‘대표가 정할 일’부터 처리하라고 안내하세요. 앱을 쓰기 전에 넣은 기성·입금에는 입력 시각이 없습니다.
- 변경공사 청구·회수(D-84)도 환경변수·스키마 변경이 없습니다(변경공사에 `log`·`nextFollowUp`·`decisionNote`·`approvalBasis`·`reclaimOf`·`noReclaim`·`createdBy`, 원가에 `noClaim`이 붙지만 JSON 안). 운영을 시작하면 공무에게 ① 설계변경 추가 원가가 생기면 ‘기성·수금 → 변경공사 — 청구·회수’에서 바로 만들고 ② 발주처에 보낼 때 ‘발주처 청구’와 다음 확인할 날을 정하고 ③ 확인할 때마다 ‘기록’을 남기라고 안내하세요. 이미 쌓인 변경공사(앱 이전·이관분)에는 다음 확인할 날이 없어 ‘챙길 것’에 뜨니, 첫 주에 ‘기록’으로 날을 정해 주세요. 변경공사로 청구한 원가는 현장에서 고치거나 취소할 수 없습니다.
- 숫자 맞추기 점검(D-85)도 환경변수·스키마 변경이 없습니다(새 묶음 `profitAdjustments`는 기존 `records` 표에 저장 · 지우지 않음). 실제 장부를 이관한 뒤와 매달 마감 전에 ‘자료 이관·점검’ 맨 위 점검이 모두 초록인지 확인하게 하세요. 빨간 줄은 계산 오류라 개발 담당이 봐야 합니다(대시보드 처리 대기에도 뜸). 노란 줄은 중복 입력 의심 등이라 공무가 장부를 보고 판단합니다.
- ❌가 하나라도 있으면 종료 코드 1입니다. 고친 뒤 다시 돌립니다.
- 외부 감시 서비스에는 `/api/health`를 등록하면 장애를 알림으로 받을 수 있습니다.

AI API 키는 현재 쓰지 않습니다. 위험 분석은 규칙 기반이며 AI 연결은 대표 승인 후 별도로 진행합니다.

## 4. 백업과 복구

| 방법 | 들어가는 것 | 주기 | 담당 |
|---|---|---|---|
| 앱 **자료 이관·점검 → 전체 자료 내려받기** (`taekang_backup_날짜.json.gz`, 압축) | 현장·원가·기성·변경공사·출퇴근·보고·작업 인원·지시·요청·월 마감·이력 전체·사용자 목록. 비밀번호·로그인·QR 단말기 비밀값은 제외 | 월 1회 (월말) | 대표 |
| 앱 **같은 카드 → 사진 백업 내려받기** (`taekang_photos_YYYY-MM.zip`, 달마다) | 그 달 사진 원본 + 목록(photos.json). 풀면 `날짜_현장_설명_번호.jpg` | 월 1회 (월말) | 대표 |
| Supabase 자동 백업 | DB 전체 (사진 원본 포함) | 요금제에 따라 매일 | 자동 (요금제 확인) |
| 수동 DB 백업 (`pg_dump`) | DB 전체 | 분기 1회 · 큰 변경 전 | 시스템 관리자 |

- 전체 자료 파일은 압축본입니다(30일 운영 자료 48KB, 내용이 섞인 1년치 시험 자료 약 1.7MB — 원문 약 14MB). 서버가 흘려보내는(스트리밍) 방식으로 내려줘 서버 응답 한도(Vercel 4.5MB)에 걸리지 않습니다 (D-86). 압축을 풀면(7-Zip 등) 예전과 같은 JSON입니다.
- 사진은 크기 때문에 달마다 따로 받습니다. 브라우저가 사진을 한 장씩 받아 ZIP으로 묶으므로 **PC에서** 받습니다(30일 76장 기준 두 달 합 2MB · 1초 미만, 한 달 수백 장이면 몇 분).
- **사고 복구(같은 시스템)는 DB 백업으로 합니다** — Supabase 복원 또는 `pg_dump` 복원 (시스템 관리자).

### 4-1. 새 시스템으로 옮기기 (계정 이전 · 서버 이전 · D-86)

미래AI랩 계정에서 태강 명의 Supabase·Vercel로 옮길 때, 또는 서버를 바꿀 때의 순서입니다. **빈 시스템에서만 됩니다** — 회사가 하나라도 있으면 거부하므로 쓰고 있는 자료를 덮어쓸 수 없습니다.

1. (예전 시스템) 직원에게 옮기는 시각을 알리고, 그 뒤로는 입력하지 않게 합니다.
2. (예전 시스템) 대표가 **전체 자료 내려받기** + 사진이 있는 달마다 **사진 백업 내려받기**.
3. (새 시스템) 태강 명의 Supabase·Vercel로 배포하고 `SETUP_CODE`를 등록합니다 (3절).
4. (새 시스템) 첫 화면 `/setup` → **백업 파일로 시작 (계정 이전)** → 백업 파일 선택 → 미리 보기(회사·백업 시각·자료 건수) 확인 → 대표 이메일(백업 속 대표 계정) + **새 비밀번호** + 설정 코드 → **백업 파일로 시작하기**.
5. 결과 화면의 ‘이어서 할 일’을 차례로:
   - **로그인 쪽지 다시 나눠 주기** — 비밀번호는 백업에 없어 대표 외 모든 사람이 ‘첫 로그인 전’입니다. 현장 직원은 **시범 운영 준비**에서 골라 인쇄하면 임시 비밀번호가 새로 들어갑니다. 본사 관리자·발주처는 **운영 관리 → 사용자**에서 사람마다 ‘비밀번호 초기화’ → ‘로그인 쪽지 인쇄’.
   - **사진 백업 올리기** — 자료 이관·점검 → 전체 자료 백업 → **사진 백업 올리기 (.zip)** (내려받은 ZIP을 풀지 말고 그대로). 원본이 없는 사진만 채우고 이미 있는 것은 바꾸지 않아 여러 번 올려도 됩니다. 올리기 전 사진 자리에는 ‘사진 원본 없음’ 그림이 보입니다.
   - **현장 QR 단말기 다시 연결** — 단말기 비밀값은 옮겨지지 않아 ‘해제됨’으로 남습니다. 출퇴근 화면에서 새로 등록합니다.
6. 대시보드·월 마감·**숫자 맞추기 점검**(자료 이관·점검 맨 위)을 예전 시스템과 비교합니다. 결과 화면에도 점검 결과가 나옵니다.
7. 휴대폰 알림은 새 시스템에서 대표가 ‘회사 휴대폰 알림 켜기’를 다시 한 번 누르고(알림 키는 백업에 넣지 않음 · D-91), 직원이 각자 다시 켭니다(알림 구독은 기기마다라 옮겨지지 않음).

옮겨지는 것과 안 옮겨지는 것:

| 옮겨짐 | 안 옮겨짐 (다시 할 일) |
|---|---|
| 회사·현장·계약·예산·원가·기성·입금·변경공사·월 마감·이익 조정 기록·출퇴근(보관 기간 지난 좌표는 지운 채)·보고·사진 기록·작업 인원·지시·요청·하자·자재·보고서 링크·하자 접수 링크(새 시스템이 같은 인터넷 주소를 쓸 때 그대로 열림 — 주소가 바뀌면 다시 보내기)·활동 이력 전체·사용자(같은 아이디·역할·담당 현장·비활성 여부) | 비밀번호(대표는 복원 때 새로, 직원은 로그인 쪽지) · 로그인 상태 · 사진 원본(사진 백업 올리기) · QR 단말기 연결 · 휴대폰 알림 구독 · 하자 접수자에게 보낸 ‘진행 확인’ 주소(백업에 비밀값을 넣지 않음 — 접수 기록은 그대로) · 오류 기록 |

- 시험 결과: 30일 운영 자료(현장 3·원가 23·보고 71·사진 76·출퇴근 133·이력 677건)를 백업 → 빈 DB 복원 0.34초 → 사진 ZIP 2개 올리기 → 화면 자료 34개 묶음이 원본과 **완전히 같고** 숫자 맞추기 점검 오류 0건. 1년치 규모(약 4.6만 줄) 복원 2.1초.
- 압축 3MB가 넘는 백업은 화면이 3MB 조각으로 나눠 올린 뒤 합쳐 복원합니다(1년치 시험 자료 2조각 2.1초). 압축 48MB(16조각)를 넘는 아주 큰 자료와, 압축을 푼 원문이 64MB를 넘는 자료(대략 4년치 이상)는 DB 복원으로 옮깁니다.

- 잘못 넣은 엑셀 자료는 7일 안에 **자료 이관·점검 → 최근 가져오기 → 가져오기 취소**로 되돌립니다.
- **로그인**: 쓰는 동안 계속 유지됩니다(30일 넘게 안 쓰면, 그리고 처음 로그인 후 180일마다 다시 로그인 · D-48). 휴대폰을 잃어버리면 **운영 관리 → 사용자 → 모든 기기 로그아웃**(알림도 해제). 사용자 추가·가입 승인·승인 안 함·비밀번호 초기화·일시 정지·로그아웃은 활동 이력 ‘사용자 관리’에 남습니다.
- **오류·의견**: 매주 확인합니다. 앱 오류 기록이 쌓이면 미래AI랩에 알립니다. 현장 의견은 ‘반영함/보류(이유)’로 처리하면 보낸 사람 휴대폰에 결과가 갑니다(D-47).
- 원가 한 건은 현장 상세 → 원가에서 무효 처리합니다.
- 활동 이력(누가·언제·무엇을)은 지워지지 않습니다.

## 5. 관리자가 하는 일 (요약 — 자세한 순서는 앱 **사용 안내 → 본사 관리자**)

| 일 | 화면 | 주의 |

| 직원 입사 | 운영 관리 → 사용자 → 추가 | 임시 비밀번호가 한 번만 보입니다. 본인에게 직접 전달합니다 |

| 비밀번호 분실 | 운영 관리 → 사용자 → 비밀번호 초기화 | 비밀번호를 여러 번 틀리면 10분 동안 잠깁니다 |
| 새 현장 | 운영 관리 → 현장, 출퇴근 현황 → 현장 위치·반경 | 담당자·공정 단계까지 넣어야 보고·일정이 동작합니다 |
| 현장 QR 태블릿 | 출퇴근 현황 → 단말기 만들기 → 태블릿에 연결 코드 | 태블릿을 잃어버리면 즉시 **해제** |
| 진행 중 현장의 지난 자료 | 자료 이관·점검 | 엑셀 양식 → 채워 저장 → **엑셀 파일 그대로** 올리기(CSV도 됨). 오류가 있으면 엑셀 행 번호와 함께 알려주고 아무것도 넣지 않습니다. 예전 형식(.xls)은 .xlsx로 다시 저장 |
| 실사용 확인 | 사용 현황 | 정착이 안 된 직원은 교육이 먼저입니다 |
| 통신 불량 출퇴근 확인 | 지시·확인 → 근태 수정 요청 (**‘통신 불량 · 자동’**) | 지하 등에서 누른 출퇴근이 늦게 도착하면 시스템이 ‘누른 시각 확인’ 요청을 만듭니다. 기록은 도착 시각이고, **승인하면 누른 시각**으로 바뀝니다. 누른 시각은 휴대폰 시계 기준이므로 의심되면 현장소장에게 확인 후 반려합니다 (D-55) |

| 새 직원 교육 | 사용 안내 → **그림 안내 1장** | A4 한 장 인쇄해 첫날 같이 보며 출근·보고를 한 번씩 눌러 봅니다. 본사 전화는 운영 설정에 넣으면 자동으로 찍힙니다 |
| 설계서 | 관리 → **상세설계서** | 화면·권한·데이터 구조가 바뀌면 이 문서도 자동으로 바뀝니다(시스템 기준). 외부 감사·인증 자료로 인쇄해 쓸 수 있습니다 |
| 단계 검수 | 관리 → **검수 확인서** | 단계·기간 선택 → 인쇄 → 발주자 확인·서명. 체크는 저장되지 않으므로 서명한 종이를 보관합니다 |

## 5-1. 시범 운영 첫날 (관리 → **시범 운영 준비**)

1. 전날: ‘시범 운영 준비’ 맨 위가 **“시작할 수 있습니다”**인지 확인합니다. 빨간 항목(본사 전화번호·현장 위치·현장 담당·담당 현장 없는 직원)을 먼저 고칩니다.
2. 직원을 모두 골라 **로그인 쪽지**를 인쇄합니다. 첫 로그인 전인 사람은 임시 비밀번호를 새로 만들어 넣습니다. **그림 안내 1장**도 사람 수만큼 인쇄합니다.
3. 당일 직원 1명당 약 5분:
   1. 쪽지 QR로 접속합니다.
   2. 임시 비밀번호로 로그인한 뒤 새 비밀번호를 정합니다.
   3. 홈 화면에 아이콘을 만듭니다.
   4. ‘내 휴대폰 점검’을 합니다.
   5. 현장에서 ‘출근하기’를 누르고 위치 기록에 동의합니다.
   6. 보고를 1번 보내 봅니다.
4. 그 자리에서 ‘시범 운영 준비’의 직원 줄이 **첫날 준비 끝**으로 바뀌는지 봅니다.
5. 첫 주에는 매일 **사용 현황**으로 빠진 사람에게 전화합니다. 같은 질문이 두 번 나오면 미래AI랩에 알려 주세요(그림 안내에 추가).

## 6. 개인위치정보 (출퇴근 GPS)

- 위치는 **출근·퇴근·보고를 누를 때만** 한 번 기록합니다. 처음 출근할 때 동의 화면이 나오고, 동의 기록(시각·문구 판)이 남습니다.
- 위치 기록은 대표·관리자만 봅니다. 현장 직원은 자기 기록만 봅니다. 발주처에는 보내지 않습니다.
- **회사가 정할 것**(별지 제5호) — 법률·노무 전문가와 확인 후 대표가 **운영 관리 → 개인위치정보**에서 설정합니다(D-43):
  - **보관 기간**: 지나면 좌표·거리·오차를 매일 자동으로 지웁니다. 출퇴근 시각과 현장 안/밖 판정은 근무 기록으로 남습니다. 정하기 전에는 지우지 않고 화면에 경고가 뜹니다.
  - **좌표를 볼 수 있는 사람**: 대표만 / 대표·관리자. ‘대표만’이면 서버가 관리자에게 좌표를 아예 보내지 않습니다.
  - **고지 문구**: 같은 화면 ‘직원에게 알리는 내용’에 직원이 보는 문구가 그대로 나옵니다. 고쳐야 하면 미래AI랩에 요청합니다(문구 판이 올라가 다시 동의를 받음).
  - 위치정보 관련 신고·등록 필요 여부 (전문가 확인)
- **직원 열람·철회**: 직원은 휴대폰 ‘내 정보 → 내 위치 기록’에서 자기 기록을 보고 ‘위치 기록 그만두기’를 누를 수 있습니다. 누르면 남은 좌표를 바로 지우고, 출퇴근은 ‘위치 없음’으로 계속됩니다.
- **동의 기록**: 동의한 시각·문구 판·그때 알린 보관 기간·열람 범위가 남습니다. 회사가 조건을 직원에게 불리하게 바꾸면(더 오래·더 많은 사람) 다음 출근 때 다시 동의를 받습니다.
- **퇴사·본인 요청**: ‘직원별 동의 현황’에서 ‘좌표 지우기’(사유 기록, 되돌릴 수 없음). 규칙 변경·삭제는 모두 활동 이력(종류: 개인위치정보)에 남습니다.
- 활동 이력 문구에는 거리·오차를 쓰지 않습니다(좌표를 지워도 문구로 위치가 남지 않게).

## 6-1. 데이터가 쌓였을 때 (성능)

- 1년치(현장 6곳·직원 20명, 약 3.4만 건)에서 명령 1건이 약 0.2초 걸립니다(메모리 재사용 전 0.5초 · D-50). 현장 휴대폰은 최근 60일만 받습니다(압축 약 17KB).
- 약 2년치(주요 기록 4.5만 건)부터 느려지기 시작합니다(3년치 측정 1.6~1.8초).
- 그 시점이 되면 **자료 이관·점검 → 데이터 규모**가 노란색 경고로 바뀝니다. 이때 ‘오래된 기록 보관 정리(아카이브)’ 작업을 유지보수로 진행합니다(D-34).
- 측정 방법: `npm run perf` (3년치는 `PERF_DAYS=900 npm run perf`).
- **아침 출근 몰림** (1년치, 실제 Postgres + 풀러, 로컬 측정 · D-50)
  - 20명이 같은 순간 출근을 눌러도 오류 없이 처리됩니다. 가장 늦은 사람은 약 3.5초를 기다립니다.
  - 실제로는 몇 분에 걸쳐 나눠 누르므로 거의 기다리지 않습니다.
  - 서버 함수 시간 한도는 명령·화면 데이터 30초, 백업 60초로 넉넉히 잡았습니다.
- **DB를 직접 고쳤을 때**(Supabase 화면에서 SQL로 수정 등)
  - 반드시 `update companies set rev = rev + 1;`을 함께 실행합니다.
  - 서버가 회사 데이터를 최대 30초 기억하므로, rev를 올리지 않으면 그 사이 명령이 고치기 전 내용을 기준으로 저장할 수 있습니다.
  - 앱 화면으로 바꾼 것은 자동으로 처리됩니다.

## 7. 문제가 생겼을 때

| 증상 | 먼저 확인 | 다음 |
|---|---|---|
| 한 사람만 로그인이 안 됨 | 사용자 화면에서 잠김·일시 정지·가입 승인 대기 여부 | 비밀번호 초기화 · 다시 사용 · 승인 |
| 모두 접속이 안 됨 | `/api/health`, Vercel 배포 상태, Supabase 상태 페이지 | Vercel 최근 배포 로그 → 직전 배포로 되돌리기 |
| 누가 바꿨는지 확인 필요 | **활동 이력** (기간·사람·종류로 검색, CSV) | 해당 화면에서 되돌리기·정정 (사유 기록) |
| 화면은 뜨는데 저장이 안 됨 | 인터넷 연결, Supabase 사용량 한도 | 현장 보고는 휴대폰에 남아 있어 연결되면 다시 보냅니다 |
| 숫자가 장부와 다름 | 자료 이관·점검의 빠진 자료, 잔여예상원가 재추정일 | 공무 확인 대기 원가가 남았는지 확인 |
| 위치가 계속 ‘현장 밖’ | 현장 위치·반경 | 큰 현장은 반경을 넓힙니다 |

유지보수 범위(무상 기간·응답 시간·추가 개발)는 계약서를 따릅니다.

## 8. 보안 수칙

1. `DATABASE_URL`·Supabase 키를 메신저·메일로 보내지 않습니다.
2. 퇴사자는 당일 일시 정지합니다. 대표 계정은 공유하지 않습니다. 로그인 화면에 회원가입 신청이 공개돼 있으니, 모르는 신청은 승인하지 않습니다.
3. 발주처 계정에는 그 발주처 현장만 연결합니다. 포털에는 내부 원가·이익·미수가 서버에서 차단되지만, 연결 현장을 잘못 고르면 다른 현장의 진행률이 보입니다.
4. 엑셀 자료를 올린 뒤 원본 파일은 회사 보관 폴더에만 둡니다.
