너는 미래AI랩의 시니어 AX 전략가, 프로덕트 디자이너, 풀스택 엔지니어, 데이터 설계자, QA 리드다. 이 작업의 목표는 단순히 예쁜 UI를 보여주는 것이 아니라, 건설현장 운영 데이터가 실제 의사결정과 행동으로 이어지는 태강지엘텍 맞춤형 인터랙티브 AX+플랫폼 MVP를 완성하는 것이다.

## 0. 참조 문서 및 실행 우선순위

1. 리포지토리의 `docs/` 폴더에 있는 **Unified v4.1 마스터 MD의 실제 전문을 먼저 읽고**, 최신 Override를 적용한다. 파일이 다른 위치에 있으면 탐색해 정확히 확인한다.
2. 충돌 시: 현재 프로젝트 명시 요구사항 → Unified v4.1 Device View Override → Unified v4.0 Evidence/Grouped IA/7 Theme/Motion Override → 본 마스터의 나머지 상세 규칙 순으로 판단한다. 단 기술·보안·사실성 관련 안전 요구사항은 절대 완화하지 않는다.
3. v4.1에 포함된 과거 문서의 '9 Theme', '별도의 가짜 Mobile Preview', '기본 v3.0이 최신' 등 구버전 지시는 적용하지 않는다. **실제 테마 7개**, **PC / Mobile / PC+Mobile**, **동일 Route·동일 Data·동일 State**를 우선한다.
4. 기존 프로젝트가 있다면 현재 파일과 구현 상태를 먼저 검사한 후 개선한다. 없다면 Next.js + TypeScript + Tailwind + Supabase 연동 준비 구조로 신설한다. 사용 가능한 기존 의존성을 존중하고, 이유 없이 재구축하지 않는다.
5. 기술선택·구현범위·미해결 사항은 근거와 함께 `DECISIONS.md`, `PROJECT_STATE.md`에 기록한다. 사소한 확인 질문으로 작업을 멈추지 말고 합리적인 기본값으로 진행한다.

## 1. 회사·프로젝트 상황

- 고객사: **(주)태강지엘텍** (유리·창호·커튼월·금속구조물 관련 시공업)
- 주요 사용자: 대표자(손익·리스크 의사결정), 본사 관리자(계약·기성·미수금·원가), 현장 담당자(공정·사진·자재·업무보고), 향후 발주처/협력사(요청·진행현황 확인)
- 핵심 문제: 현장별 계약액/예산/자재/인건비/공정/변경공사/기성/입금정보가 분산되어 **현재와 예상 수익, 원가 초과 위험, 누락된 청구**를 조기에 알아보기 어려움
- 목적: "현장이 돈을 버는지, 어디에서 이익이 줄어드는지, 지금 무엇을 조치해야 하는지"를 대표가 즉시 이해하게 만들기
- 제품명: **TAEKANG SITE INTELLIGENCE** / 보조 설명: **AI 기반 창호·유리 공사 현장 수익·공정관리 플랫폼**
- 이번 단계: 2026-10-27 화요일 첫 대면 미팅을 위한 **실제로 작동하는 영업용 High-Fidelity MVP**. 상용 ERP 완전체가 아니라 **핵심 업무흐름이 끝까지 연결된 시연용 제품**이다.
- 공개되지 않은 고객사의 매출·계약·거래처·프로젝트 상세를 사실처럼 만들어 넣지 말 것. 실제 자료가 없으면 일관된 가상 시연 데이터를 사용하고 `DEMO · 가상 시연 데이터` 배지를 항상 식별 가능하게 표시한다.

## 2. 가장 중요한 사용자 경험 — 3~4분 시연 완결

발표자가 처음 보는 이주현 대표님에게 다음 장면을 순서대로 클릭·조작하면서 보여줄 수 있어야 한다.

1. **PC 대표 대시보드**: 운영 중인 가상 현장 3개, 전체 계약 규모, 프로젝트별 예상이익·예상이익률, 기성/미수금, 위험 알림을 한눈에 표시.
2. **현장 A 상세**: 선택한 가상 창호·유리 공사현장의 계약금액 10억 원, 현재 총예상원가(EAC) 8.5억 원, 예상이익 1.5억 원, 예상이익률 15%를 보여줌. 원가를 '발생원가'와 '잔여 예상원가'로 나누되 지표 정의를 표시할 것.
3. **모바일 현장 보고 입력**: 담당자 Demo Role로 A현장에 추가 자재비 3,000만 원 + 추가 인건비 1,000만 원을 입력하고 필요하면 현장사진·사유를 첨부. 저장 후 실제 공통 데이터 소스의 비용 이벤트가 업데이트되어야 함.
4. **PC 즉시 반영**: 같은 현장의 총예상원가 8.9억 원, 예상이익 1.1억 원, 이익률 11%, 이익 감소액 4,000만 원이 정확히 표시됨. 하드코딩된 숫자교체 애니메이션이 아니라 비용 합산→예상원가→예상이익 재계산 구조여야 함.
5. **AX 판단 → 실행 → 결과**: 규칙 기반 위험 감지로 `이익률 15%→11%`, `비용초과`, `설계변경 청구검토` 안내. 관리자가 '추가공사 청구가능성 검토' 조치 담당자를 지정하고 상태를 '진행 중→완료'로 바꾼 뒤, 실제 조치기록과 `proof_event`를 남김.
6. **대표자 보고서**: 변경 전후 수익 비교, 관련 현장보고, 위험분석, 조치상태가 요약된 실시간 리포트 확인. Demo Reset으로 미팅 직전 초기상태 복구 가능.

이 흐름이 이번 프로젝트의 최우선 P0이며, 시각효과·추가기능보다 항상 우선한다. 시연은 실제 Route를 안내하는 `Presentation Mode`로 제공하되, 파워포인트식 가짜 슬라이드로 대체하지 않는다.

## 3. 화면 설계 — PC 4개 + Mobile 핵심 화면 2개

### PC
- `/dashboard`: 대표자 전체 현장 통합 대시보드. KPI 4~6개, 손익 위험 현장 순위, 최근 보고, 미수금, AI 권장조치.
- `/sites/[id]`: 현장별 수익·원가·공정 상세. 원가항목, 진행률, 계약·변경공사, 현장사진, 기성/입금 Drill-down.
- `/insights`: AI/규칙 기반 현장 위험 분석과 관리자의 승인·담당자 배정·조치 실행·결과확인.
- `/finance`: 기성청구·입금·미수금·변경공사·보고서. '청구액'과 '입금액', '계약액'과 '예상이익' 개념을 절대 혼동하지 말 것.

### Mobile
- `/field`: 현장담당자 화면. 현장 선택, 오늘 공정, 사진·메모, 추가 비용 입력, 작성이력, 완료확인. 한 손 조작이 편해야 함.
- `/my-actions`: 담당자에게 배정된 위험조치 확인, 사유·진행상태 업데이트, 확인사진/메모 제출.

### AX + 플랫폼 연결의 최소 완결
- `/partner`: 미래 확장용 **발주처/협력사 상태 포털의 작은 실제 작동형 Surface**. 데모 상대방은 현장 진행률 및 승인된 상태정보만 확인하고 변경공사 검토 요청 1건을 등록할 수 있다.
- 요청 등록 → 내부 `/insights` 또는 현장별 요청함에 반영 → 관리자의 검토/승인 → `/partner`에서 처리 상태가 바뀌는 **양방향 Closed Loop**를 구현한다.
- 파트너에게 내부 원가/이익/미수금/다른 고객 현장정보가 노출되지 않도록 한다.
- 이 포털은 핵심 3~4분 시연의 성공을 방해하지 않는 범위에서 경량화해 완성한다. 로그인 결제, 발주처 전체 ERP, 협력사 마켓플레이스, 전자계약 전체 구현은 이번 범위에서 제외한다.

### 기타 필수
- `/why-ax`: 회사 업종 맞춤 기획의도, 기존 업무→AX 전환, 수익보호 논리, 실제 실증 전/후 구분, 향후 B2B 확장 방향.
- `/evidence`: 예시 Proof Event, 지표 측정 계획, 실증 준비 상태.
- `/settings`: 테마, 글자 크기, Demo Role 전환, Demo Reset, 데이터 샘플·CSV 가져오기/필드 구조 안내.
- `/presentation`: 별도 가짜 화면이 아니라 실제 Route를 5~6개 Step으로 안내하는 시연 모드. Next/Back/Skip/Exit, 초점 복구, 오버레이 잔존 방지.

## 4. 데이터·계산·정합성

필수 엔티티 예시:
`sites`, `site_contracts`, `cost_budgets`, `cost_entries`, `cost_forecasts`, `progress_updates`, `site_photos`, `change_orders`, `progress_billings`, `payments_received`, `partner_requests`, `risk_signals`, `actions`, `proof_events`, `activity_logs`, `demo_scenarios`, `roles`.

중복 테이블을 억지로 만들지 말고 도메인 정합성을 유지할 것. TypeScript 타입, Repository 인터페이스, Validator, 계산 유틸을 분리한다.

계산식:
- `EAC = 이미 발생한 누적원가 + 완료까지의 예상 잔여원가` (또는 별도 조정 가능한 전체 예상원가)
- `Expected Profit = 계약금액 + 승인된 변경계약금액 - EAC`
- `Expected Margin % = Expected Profit / (계약금액 + 승인된 변경계약금액) * 100`
- `Outstanding = 확정된 기성청구액 - 실제 수금액`
- 추가 비용 이벤트가 기존 EAC에 반영되는 방식을 데이터 모델에 명시하고 **중복 계산 금지**.
- 변경공사 요청/예상 청구 가능금액을 승인된 계약 증액으로 자동 가산하지 않는다.
- 금액 단위(원·만원·억원)와 부가세 기준을 화면에서 구분한다.

데모 Seed는 창호·유리·커튼월 업종에 맞는 **가상 현장 3개**, 계약·원가·공정·기성·입금 내역과 2~3개 위험 시나리오를 제공한다. 회사 매출, 실제 발주처명, 프로젝트명 등의 미확인 사실은 사용 금지. 미팅용 10억→8.5억→추가 0.4억→8.9억→1.1억 시나리오는 반드시 재현 가능해야 한다.

### 실제 데이터가 없을 때의 필수 동작
- 문서의 `Demo Seed Data + Data Repository Layer + Import/Replace Point` 원칙을 따른다.
- Supabase 환경변수/권한이 준비되어 있으면 실제 DB 테이블·RLS·Auth를 사용한다.
- 준비되지 않았다면 local demo repository에 안전한 샘플을 저장하고 세션 사이에서 시연 데이터가 유지되게 한다. 단 데모 저장소를 '운영 DB 연결 완료'라고 표시하지 않는다.
- `CSV 샘플 내려받기`, `가져오기`, `실데이터 전환 경로`를 준비해 향후 실제 자료와 대체할 수 있게 한다. CSV는 유효성 검사와 오류 표시를 구현한다.
- 상태 업데이트 후 대시보드, 모바일, 보고서, 리스크, 파트너 포털이 같은 정보로 동기화되어야 한다.

## 5. AI/로직 구성 — 실 AI와 예시 AI를 정확히 구분

- **금액·이익률 계산은 결정론적 코드**로 구현한다. LLM에게 산술·실제 숫자 계산을 위임하지 않는다.
- 위험 신호: 이익률 하락, 예산 초과, 공정 대비 원가 이상, 기성 미수, 미승인 변경공사 등을 데이터 기반 규칙으로 우선 감지한다.
- AI API Key와 명시적 사용 승인이 있으면 `현장 위험요인 요약·우선조치 제안` **핵심 1개**만 실제 서버 API로 연결한다. 입력 데이터 범위·민감정보·타임아웃·오류처리를 명시.
- AI API가 없으면 **'규칙 기반 진단'**으로 정확히 표시하고 AI Ready 설명 및 향후 연결 인터페이스를 제공한다. API를 실제 호출한 척하거나 '실시간 AI 학습 중' 같은 표현 금지.
- AI/로직 판단 → 관리자 승인·실행 → 결과 확인 → Evidence 저장 흐름이 실제 작동해야 한다.
- Proof Event는 `trigger`, `decision`, `decision_method`, `human_approval`, `action`, `result`, `kpi_before`, `kpi_after`, `data_source`, `user_id`, `created_at`, `status` 등 최소 필드를 포함한다.
- 도입 전후 성과와 실증률을 모르면 `Baseline not yet established` 또는 `실증 예정`으로 표시한다. 개선률을 지어내지 않는다.

## 6. 디자인 및 사용성

- 이전 태강지엘텍 AX프론트 시안과 일관된 **프리미엄 B2B 현장 SaaS**: 다크 차콜/네이비 Shell, 절제된 오렌지 포인트, 순백색 업무 Surface, 건설/창호 사진의 제한적 사용, 큰 한글과 높은 대비.
- `docs/references/taekang_front_pc.png`와 `docs/references/taekang_front_mobile.png`가 있다면 실제 사용자가 선호한 태강지엘텍 AX프론트 레퍼런스로 `Front Reference First` 원칙을 적용해 구조·색채·글자 크기·정보 밀도에 충실하게 재현한다. 없으면 업종 맞춤 브랜드 레이어를 직접 설계한다.
- 첫 화면은 임원/대표가 5초 안에 위험 현장·수익 변화·조치 필요 사항을 이해할 수 있어야 한다.
- 표·카드·수치의 정보 우선순위를 분명히 하고 글자가 지나치게 작거나 조밀하지 않게 한다. 색만으로 정상/위험을 구분하지 않는다.
- 그룹 네비게이션: 운영 / 고객·정산 / AX·성과 / 관리 총 3~4개 그룹, 대표 1차 메뉴 8~12개 권장. 중첩 메뉴 1단계. Group별 Color Hue 통일.
- v4.1의 **Canonical 7 Theme**를 지원하고 전체 앱·미리보기에서 테마 전환. 기본 테마는 업종·시안과 잘 맞는 하나로 선정하며 회사 고유 오렌지 강조 요소는 Semantic/Brand Token으로 일관되게 설계.
- Hover/Pressed/Active/Selected 상태, 절제된 KPI/Chart/Route Motion, Reduced Motion 지원. 가짜 버튼·Dead End 금지.
- 현장 모바일 UX는 글자·터치대상 크게, 사진 첨부·보고 제출을 가장 빠르게, 불필요한 입력 최소화.
- 이미지 부재시 저작권·출처 불명 사진을 실제 현장 사진처럼 사용하지 않는다. 업종 맞춤 데모 이미지 또는 정직한 플레이스홀더 사용.

## 7. v4.1 Device View — 반드시 구현

Desktop 상단에 `[ PC ] [ Mobile ] [ PC+Mobile ]` 선택 UI를 제공한다.
- PC: 정상 Desktop Product View.
- Mobile: 실제 **390px viewport**로 같은 앱의 같은 route를 Mobile Frame에서 렌더링 (스크린샷이나 단순 CSS 확대/축소 금지).
- PC+Mobile: 기본 `PC 67% : Mobile 33%`, 오른쪽 모바일 Phone Frame, 필요 시 Sticky. 동작하는 같은 데이터와 상태를 보여줄 것.
- Parent↔iframe Route 양방향 Sync, 같은 Origin 확인, 무한 메시지 Loop 방지, iframe 안에 다시 Preview 생성하지 않기.
- 화면 폭 390, 430, 768, 1024, 1280, 1440, 가능한 경우 1920 기준 확인. 모바일 Bottom Nav·Safe Area·Modal·Table 가로 넘침 검증.
- 대표가 PC에서 보고 있는 A현장을 모바일에 함께 보여주고, Mobile 입력 후 PC 수익 수치가 실제 갱신되는 장면을 완성한다.
- PC용/모바일용 가짜 데이터를 별개로 만드는 행위는 P0 FAIL.

## 8. Role / 보안

- 대표자 / 본사관리자 / 현장직원 / 발주처·협력사 데모 Role을 구분한다.
- 로그인·Supabase RLS가 실제 활성화되지 않았다면 Demo Role Switcher는 단지 **권한 프리뷰**임을 표시한다. 실제 보안을 제공하는 것처럼 표현하지 않는다.
- 실 DB 사용 시 회사/현장 단위 접근제어와 비공개 데이터 필터링, Server-Only Secrets, 데이터 조회·변경 검증이 필수다.
- 외부 포털은 내부 수익과 원가를 절대 보여주지 않는다. 모든 금액·실적은 샘플로 구분한다.
- 불필요한 고객 개인정보나 실제 프로젝트 도면은 저장하지 않는다.

## 9. 우선순위 · 본 시연에서 하지 않을 것

### P0 — 반드시 완성
- 런칭 가능한 빌드, 데모 데이터/리셋
- 대시보드 → 현장 상세 → 모바일 비용입력 → PC 손익 계산변화 → 위험알림 → 조치 → Proof Event → 보고서
- PC+Mobile 실제 동일 Route/Data 동작
- 역할별 핵심 사용화면, 최소 파트너 요청 Closed Loop
- 모달·폼·업데이트·빈상태·오류상태·기본 접근성·반응형
- 기획의도(Why AX), 가상데이터 표시, 금융기관 성과 과장 금지

### P1 — P0 완료 후 강화
- CSV 가져오기/교체, 시연 안내 모드, 7개 테마 전체 QA, 간결한 12주 Evidence 계획, 차트/모션 완성도, 리포트 인쇄형 스타일

### 이번에 제외
- 실제 회계 ERP·은행 자동 연동, 전자세금계산서 자동 발행, BIM/도면 자동견적, 영상 AI 검측, 발주처 정식 결제/계약, 복수 회사 SaaS 과금, 실제 정책자금 신청 자동화, 특허 성과 자동 주장, 구현되지 않은 AI 예측 정확도 주장
- '향후 가능' 아이디어는 NEXT/BACKLOG로 분리하고 완성 기능과 섞지 말 것.

## 10. 실행 순서

1. `/docs`와 첨부 Master v4.1을 실제로 읽고 우선순위/충돌을 `PROJECT_SPEC.md`에 기록.
2. 현재 레포를 검사하고 기존 구현을 재사용하면서 P0 데이터 모델·상태 흐름을 설계.
3. 첫 빌드부터 대시보드/모바일/Device View의 공통 Shell 및 7 Theme 구조를 확립. 여러 Phase 후에 테마를 억지로 붙이지 말 것.
4. 가상 현장 3개의 일관된 Seed, 변동원가 계산 테스트, 데이터 저장/복원/초기화를 완성.
5. **핵심 Demo Flow를 우선 완성**하고 최소 1회 끝까지 직접 클릭·검증.
6. 파트너 포털의 요청→본사 확인→파트너 상태갱신 Closed Loop 구축.
7. Guided Presentation Mode, Why AX, Evidence, Settings를 맞춤형으로 완성.
8. UI Motion/Responsive/Role/빈 상태/접근성, 누락 기능, 느슨한 문구, 비정상 표시를 QA.
9. 실행 가능한 배포 환경 설정과 README/프로젝트 인수인계 작성. GitHub 반영은 사용자 권한·자격증명이 준비된 범위에서 진행; 권한이 없으면 코드를 안전하게 준비하고 필요한 정확한 명령만 제시한다.
